# Playback Rental — кастомная админка на headless Payload + переезд в Docker

## Context

Сейчас: `apps/web` (Astro) — витрина, `apps/cms` (Payload 3 на Next) — бэкенд и админка.
Оба запускаются отдельными dev-серверами, Postgres на хосте, Docker в проекте нет.

Две задачи:

1. **Кастомная админка.** Дизайн админ-панели есть в макете (экран «Админка»): тёмный сайдбар,
   KPI-карточки, таблицы заказов и склада, Gantt-календарь, карточки клиентов, бары аналитики.
   Payload должен стать **чисто headless-бэкендом**, весь интерфейс управления — свой.
2. **Docker + один порт.** Всё поднимается одной командой и отдаётся на **одном** публичном порту.

Однопортовая схема **уже работает**: `apps/web/src/middleware.ts` проксирует `/admin`, `/api`,
`/_next` на CMS. Порт 3000 — внутренний, наружу нужен только порт витрины. В Docker он вообще
не будет публиковаться.

### Целевой стек

**Astro + headless CMS (Payload) + Docker + docker compose.**

Сквозное правило: **всё через Docker** — и запуск, и сборка. Локальные `pnpm dev` / `pnpm build`
перестают быть рабочим сценарием; на машине нужны только Docker и docker compose.
Версии Node и pnpm пинятся в образе — это и есть воспроизводимость.

### Решения, принятые с владельцем

| Вопрос | Решение |
|---|---|
| Объём замены админки | **Полная**: свой UI закрывает и просмотр, и всё редактирование |
| URL-схема | `/admin` — кастомная, `/cms` — штатная Payload |
| Порядок | **Сразу всё целиком**, отключение Payload-админки — последним шагом |
| Docker | web + cms + postgres; публикуется только web |
| Режимы | dev (hot-reload) и prod |
| Источник дизайна | Экран «Админка» из `Playback Rental - прокат техники.html` |

Ранее решено и остаётся в силе: вкладка **«Контент» — вне объёма**; **«Клиенты» — заказы,
сгруппированные по клиенту**, отдельной CRM-коллекции нет.

## Находки, меняющие реализацию

Проверено чтением кода (включая внутренности Payload/Next в `node_modules`).

**1. Прокси портит все сжатые ответы — вероятная причина «неостилованной админки».**
`middleware.ts` копирует все заголовки апстрима, включая `content-encoding: gzip`, но undici уже
распаковал тело. Браузер пытается разжать несжатое → HTML часто выживает, CSS/JS нет. Это ровно тот
симптом («переменные применяются, стили компонентов нет»), который записан в `CLAUDE.md` как
нерешённый. **Чинится тремя строками и должно быть сделано первым** — иначе `/cms` как страховка
непригоден.

**2. Server Actions Payload сломаются через прокси.** Next сверяет `origin` с `host`; middleware
подменяет `host` на внутренний → `Invalid Server Actions request`. Нужен
`experimental.serverActions.allowedOrigins` в `next.config.mjs`, иначе сохранение документа в `/cms`
падает с 500. **Проверить до того, как полагаться на `/cms`.**

**3. Для SSR-запросов нужен `Authorization: JWT`, а не проброс куки.** Payload при наличии `csrf`
и отсутствии `Origin`/`Sec-Fetch-Site` считает запрос неаутентифицированным — а серверный `fetch`
не шлёт ни того, ни другого. Значение берётся из куки `payload-token`.

**4. `PUBLIC_PAYLOAD_URL` ломает картинки в Docker.** `mediaUrl()` подставляет его в URL, но
`PUBLIC_*` инлайнится на **этапе сборки** и попадает в браузерный бандл — а `cms:3000` из браузера
не резолвится. Нужно разделить: серверная база (`CMS_INTERNAL_URL`, рантайм) и браузерная (`''`,
same-origin через прокси).

**5. В production Payload не пушит схему.** Пуш работает только при `NODE_ENV !== 'production'`,
флагом не включается. Миграций в проекте нет → для prod нужны сгенерированные миграции и
`payload migrate` на старте.

**6. `routes.admin: '/cms'` требует переименования папки** `app/(payload)/admin` → `.../cms`,
иначе `generate:importmap` не найдёт папку. Плюс правки импортов в `layout.tsx` и `[[...segments]]`.

**7. Корень репозитория — тоже workspace-пакет** (легаси Vite-приложение, ~60 зависимостей).
Установка в контейнере обязана быть `--filter <pkg>...`, иначе тянется лишнее и второй React.

**8. Товары нельзя создать ни в какой админке уже сейчас**: `moySkladId` одновременно `required` и
`readOnly`. Товары появляются только через `sync:moysklad`. Значит экран товаров — это **список +
редактирование, без создания**. Это убирает из объёма целую форму.

**9. Мелкое**: у `apps/web` нет `.env` (всё на дефолтах); куки Payload по умолчанию `secure: false` —
для HTTPS надо включить; стоит задать `serverURL`, чтобы убрать шум в логах и починить ссылки
восстановления пароля.

## Источник дизайна

Единственный источник правды — **`Playback Rental - прокат техники.html`** в корне проекта.
Это **не обычный HTML**: самораспаковывающийся бандл (при открытии в браузере ничего не покажет).
Разметка лежит base64+gzip внутри `<script type="__bundler/manifest">`, шаблон — во вложенном
`<script type="text/x-dc">`. Рецепт распаковки записан в `CLAUDE.md`.

Распакованные копии положить в `docs/design-reference/` (шаг 0) — сейчас они только во временной папке.

Параметры экрана «Админка»: сетка `246px | 1fr`, gap 14px, тёмный липкий сайдбар `#0A0A0A` радиус 24,
пункты меню uppercase 11.5px с бейджами, «← На сайт» внизу; белая шапка (h1 28px/500 + подпись 12.5px
+ чёрная pill-кнопка, на ховере `#D62410`); KPI-ряд 4 карточки радиус 22 со сдвигом анимации;
таблица заказов `90px 1.6fr 1.4fr 1fr 110px 130px`; Gantt с легендой Аренда/Бронь/Обслуживание.

## План работ

### Шаг 0 — подготовка
- Скопировать распакованный дизайн в `docs/design-reference/`, сослаться в `CLAUDE.md`.
- Скопировать этот план в `docs/PLAN-docker-admin.md` (решение владельца).
- Зафиксировать `packageManager` в корневом `package.json` под версию pnpm из образа; добавить `.nvmrc`.

### Шаг 1 — почини инфраструктуру прокси (полдня, низкий риск)
Делается до всего остального, потому что от этого зависит работоспособность `/cms` как страховки.
- Фикс сжатия (находка 1): `accept-encoding: identity` наверх, снять `content-encoding`/`content-length` вниз.
- `serverActions.allowedOrigins` (находка 2).
- Разделение серверной/браузерной базы URL (находка 4) в `apps/web/src/lib/payload.ts`.
- Перенос Payload-админки на `/cms` (находка 6): `routes.admin`, переименование папки, правка импортов,
  перегенерация import map; в middleware `/admin` меняется на `/cms` в списке проксируемых префиксов.
- **Приёмка:** `/cms` полностью со стилями и **сохраняет документ** без ошибок в логах.

### Шаг 2 — Docker
- `compose.yaml` (prod) и `compose.dev.yaml` (dev, bind-mount + hot-reload).
- Сервисы `db` / `cms` / `web`; **публикуется только `web`**, остальные — внутренняя сеть.
- Многостадийные `Dockerfile` в обоих приложениях, контекст сборки — корень репозитория.
  База `node:22-bookworm-slim` (не alpine — из-за `sharp`/`@swc`), corepack + запиненный pnpm,
  `--frozen-lockfile --filter <pkg>...`. **`pnpm-workspace.yaml` обязателен на стадии deps** —
  в нём `allowBuilds`, без него нативные сборки пропускаются.
- **Сборка живёт внутри образов**; для CMS в ту же стадию входит `generate:importmap`, чтобы забытая
  локальная перегенерация не могла попасть в образ.
- `output: 'standalone'` — **не добавлять**: ломает `payload migrate` и скрипты синка (им нужны
  бинарники и TS-исходники), а трассировка файлов плохо дружит с симлинками pnpm.
- `.dockerignore` с **якорями** (`/src`, `/server`, `/public`…), иначе выпилится и `apps/web/src`.
- Volumes: `pgdata`, `cms_media`. Задать явный `staticDir` из env; **разово залить существующие ~330
  файлов** в volume, иначе все картинки товаров отдадут 404.
- Env: `PAYLOAD_SECRET` стабильный навсегда (иначе разлогинит всех); `WEB_URL` — **публичный** origin
  (питает cors/csrf); `CMS_INTERNAL_URL=http://cms:3000` — рантайм; `PUBLIC_PAYLOAD_URL=''`.
- Healthcheck'и (`/api/access` отвечает без авторизации) и порядок старта web → cms → db.
- Миграции: сгенерировать первую локально, коммитнуть, prod-команда — `payload migrate && next start`.
- Скрипты МойСклад: заменить `--env-file` на `--env-file-if-exists`, запускать через
  `docker compose run --rm` в отдельном профиле `jobs`.

### Шаг 3 — оболочка админки и авторизация (1–1.5 дня, низкий риск)
- `/admin/*` — обычные Astro-роуты в `apps/web` (SSR + React-острова точечно). Тот же origin, что и
  витрина, поэтому кука сессии работает без CORS.
- **Важное ограничение маршрутизации:** `/api/*` проксируется в CMS, значит собственные серверные
  эндпойнты Astro должны жить под `/admin/api/*`.
- Гард в middleware перед проксированием: нет сессии → редирект на `/admin/login?next=...`.
- Логин формой на `/api/users/login`, логаут — `/api/users/logout`, первичное создание админа через
  `/api/users/init` + `/api/users/first-register` (убирает последнюю причину заходить в `/cms`).
- SSR-чтение — строго `Authorization: JWT` (находка 3).

### Шаг 4 — дашборды (3–4 дня, низкий риск)
Логику существующих серверных вьюх (`CalendarView`, `ClientsView`, `AnalyticsView`, `AdminKpiWidget`)
перенести **в кастомные эндпойнты Payload** — запросы копируются дословно, разметка пишется по макету.
Причина: они написаны на local API с `limit: 0` и двухшаговыми выборками; переписывать это в
REST-строку — лишний риск и лишний трафик.
Новые `GET /api/admin/{kpi,calendar,clients,analytics}`, каждый начинается с проверки `req.user`
(кастомные эндпойнты не проходят через access control коллекций).
Экраны: Дашборд, Заказы (список + карточка), Календарь, Склад, Клиенты, Аналитика.
**После этого шага админка уже закрывает ежедневную работу** — хорошая точка показать владельцу.

### Шаг 5 — операции по заказам (2–3 дня, средний риск)
Смена статуса, заметки, правка позиций (количество/даты), удаление, ручной `submit`.
Средний риск из-за того, что `beforeValidate` бросает осмысленные ошибки (доступность,
`endDate <= startDate`) — их надо показывать; формат разбирается существующим `PayloadApiError`.

### Шаг 6 — редактирование каталога (4–6 дней, высокий риск/объём)
Товары (**правка, без создания** — находка 8): цена, количество, наличие, subtitle, tag, isKit,
oldPrice, массив `kitItems`, загрузка/переупорядочивание изображений. Категории и акции — CRUD.
Здесь основной объём: штатная админка бесплатно даёт валидацию, связи, дропзону загрузки,
драг-реордер массивов и защиту от ухода с несохранёнными данными — всё это пишется руками.
Делать **общие острова** (`ImageField`, `ArrayField`, `RelationPicker`), а не по форме на экран.
Загрузка: `POST /api/media` как multipart, затем привязка id к документу.

### Шаг 7 — длинный хвост (3–5 дней, средний риск)
`site-settings` (табы + массивы + аплоады), медиатека, пользователи. Наименьшая ежедневная ценность
при наибольшей площади форм — честный кандидат «оставить на `/cms`», если сроки поджимают.

### Шаг 8 — отключение `/cms` (полдня)
Только когда: всё редактируется в `/admin`, работает первичное создание админа, `sync:moysklad`
отрабатывает, и владелец неделю прожил на `/admin`. Рекомендуется убрать `/cms` из проксируемых
префиксов, но **оставить сам роут** — чтобы в аварии можно было достучаться пробросом порта.

> Честная оценка: дашборды (шаг 4) — это про точность вёрстки и почти без риска.
> Формы редактирования (шаги 6–7) — примерно вчетверо больше работы и с реальным риском:
> неверная форма payload молча не сохраняет (ровно класс бага `mutate()`/`{doc}`, уже записанный
> в `CLAUDE.md`), у загрузок двухшаговая multipart-семантика, массивам нужны стабильные ключи.
> Поэтому `/cms` не выключается до самого конца.

## Проверка

Всё на поднятом compose-стеке, без локальных запусков.

1. **Сборка**: `docker compose build --no-cache` проходит для обоих образов; `up` поднимает стек
   без ручных действий на хосте.
2. **Один порт**: опубликован только порт web; прямое обращение к портам CMS и Postgres снаружи
   должно **не соединяться**. На публичном порту работают: витрина, `/admin`, `/cms`, `/api/...`,
   отдача `/api/media/file/...`.
3. **Прокси не портит ассеты** (находка 1): у CSS из `/cms` нет `content-encoding`, тело читаемое,
   админка визуально со стилями.
4. **`/cms` реально работает как страховка** (находка 2): сохранить товар и убедиться, что в логах
   нет `Invalid Server Actions`.
5. **Авторизация**: `/admin/*` без сессии → редирект; логин ставит куку на origin витрины; одна кука
   открывает и `/admin`, и `/cms`; логаут завершает сессию. Негативная проверка: запрос с чужим
   `Origin` должен вернуть `user: null`.
6. **Картинки**: отдаются через публичный порт; в собранном клиентском бандле и в HTML **нет**
   строки `cms:3000`.
7. **Данные переживают перезапуск**: загрузить файл → `docker compose down` (без `-v`) → `up` →
   файл и содержимое БД на месте; миграции при втором старте —но-оп.
8. **Синк МойСклад** отрабатывает через `docker compose run --rm`, поля, заполняемые вручную
   (`subtitle`, `tag`, `isKit`, `kitItems`), не затираются.
9. **Регресс витрины**: каталог, товар, даты, корзина, оформление — как прежде, консоль чистая.
10. **Dev-режим**: правка строки в `.astro` и в коллекции CMS подхватывается без пересборки образа.

### Ключевые файлы
- `apps/web/src/middleware.ts` — фикс сжатия, смена префикса на `/cms`, рантайм-URL, гард `/admin/*`
- `apps/cms/src/payload.config.ts` — `routes.admin`, `serverURL`, cors/csrf, новые эндпойнты
- `apps/web/src/lib/payload.ts` — разделение серверной и браузерной базы URL
- `apps/cms/src/components/admin/*` — запросы, которые переносятся в эндпойнты
- `apps/cms/src/collections/Media.ts` — `staticDir` из env под volume
- `apps/cms/next.config.mjs` — `serverActions.allowedOrigins`
