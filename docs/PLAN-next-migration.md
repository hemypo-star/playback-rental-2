# План миграции: `apps/web` (Astro) → Next.js App Router внутри `apps/cms`

Продолжение `docs/PLAN-docker-admin.md`. Тот план построил кастомную админку на Astro
поверх headless Payload; этот — убирает раскол на два процесса, который эта конструкция
породила.

Попутно закрывается вторая, независимая проблема: движение из доставленного дизайна
при первом переносе потерялось (кривые, длительности, часть анимаций появления). Раз
разметка витрины и админки всё равно переписывается, разумно писать её сразу по спеке,
извлечённой из бандла машинно — см. 0.3 и `docs/DESIGN-SYNC.md`.

## Зачем

Не «Astro плохой», а «два приложения там, где нужно одно». Payload 3 — это Next-приложение,
и его Local API (прямой доступ к БД, без HTTP) доступен только внутри того же процесса.
Astro как отдельный сервис до него не дотягивается, отсюда весь текущий обвес:

| Что | Где | Строк | Почему существует |
|---|---|---|---|
| Реверс-прокси `/cms`, `/api`, `/_next` | `apps/web/src/middleware.ts` | 116 | один публичный порт на два процесса |
| REST-клиент + `mutate()` | `apps/web/src/lib/payload.ts` | 287 | нет Local API |
| Проброс `Authorization: JWT` | `apps/web/src/lib/admin/session.ts` | 55 | SSR-fetch не проходит CSRF-проверку Payload |
| Клиент `/api/admin/*` | `apps/web/src/lib/admin/api.ts` | 152 | REST-обёртка над данными, которые уже есть в процессе |
| 7 эндпоинтов `/api/admin/*` | `apps/cms/src/endpoints/admin/*.ts` | — | отдают JSON в Astro; 4 из них — дословные порты `/cms`-компонентов |
| `cors` / `csrf` / `serverActions.allowedOrigins` | `payload.config.ts`, `next.config.mjs` | — | разные origin'ы |
| `CMS_INTERNAL_URL` vs `PUBLIC_PAYLOAD_URL` | 3 файла | — | разные адреса для SSR и браузера |
| Второй Dockerfile + сервис `web` | `apps/web/Dockerfile`, `compose.yaml` | — | второй процесс |

Плюс главное по UX: 17 страниц админки в `apps/web/src/pages/admin/*` (~2045 строк) — это CRUD-приложение
с полной перезагрузкой на каждый переход и мутациями через руками написанный `fetch()`.

Ни одна из этих строк не про прокат техники.

## Целевая форма

Переезжает **весь сайт, не только админка**: витрина (Этап 2) и админка (Этап 3)
оказываются в одном Next-приложении, `apps/web` в конце удаляется целиком. Вариант
«перенести одну админку» рассматривался и отклонён: он экономит ~2.5 дня, но
навсегда оставляет REST-обвязку витрины (`lib/payload.ts`, 287 строк), прокси,
`cors`/`csrf`, развилку `CMS_INTERNAL_URL` / `PUBLIC_PAYLOAD_URL`, второй Dockerfile
и второй сервис — то есть ровно ту сложность, ради которой всё затевается.

Route-группы в `apps/cms/src/app/`:

```
(frontend)/   — витрина: /, /catalog, /product/[id], /checkout, /promotions/[slug], юр. страницы
(admin)/      — кастомная админка: /admin/*
(payload)/    — Payload: /cms, /api  (уже существует, не трогаем)
```

URL не меняется **ни один**. `/product/[id]`, `/catalog/[slug]`, `/promotions/[slug]`,
`/admin/*`, `/cms`, `/api/*` — всё остаётся на своих местах. SEO-риска нет.

## Стратегия: strangler, а не big bang

`apps/web` остаётся рабочим до самого конца. Меняется только направление прокси:
публичный порт переезжает на `cms` (Этап 1), и Next проксирует на Astro всё, что ещё
не перенесено. Каждый перенесённый маршрут просто выпадает из списка прокси.

Побочный эффект, приятный сразу: как только Next становится публичным, Payload оказывается
same-origin — и весь прокси в `apps/web/src/middleware.ts` можно удалить в первый же день.

Откат на любом этапе — вернуть маршрут в список прокси.

## Этап 0 — Подготовка (до единой строки переноса)

**0.1 Разгрести флаги сборки.** Сейчас в `apps/cms/next.config.mjs` стоят
`typescript.ignoreBuildErrors` и `eslint.ignoreDuringBuilds`; `next lint` насчитывает
~190 `no-explicit-any`. Втаскивать витрину и админку под эти флаги — значит потерять
типобезопасность там, где её сейчас нет проблем.

Не чинить 190 ошибок сейчас. Вместо этого — ограничить область подавления в ESLint-конфиге
существующими путями (`src/app/(payload)/**`, `src/endpoints/**`, `src/components/admin/**`,
`src/lib/rental/**`) и снять `ignoreDuringBuilds`, чтобы новый код с первого дня был под
строгим правилом. Ретайпинг старого — отдельная задача, не блокер.

**0.2 Апгрейд Next 15 → 16.3, отдельным коммитом, до миграции.**
Заодно проверить, не чинится ли сам собой `ReactPortal`/`LayoutProps` (баг связки
React 19.2 + Next 15.5, подробно описан в комментарии в `next.config.mjs`). Если чинится —
`typescript.ignoreBuildErrors` тоже снимается. Делать это *до* миграции, чтобы падение
сборки нельзя было спутать с последствиями переноса.

**0.3 Достать спеку дизайна из бандла.** Разово, до переноса — потому что Этап 2 будет
верстать по ней, а не по глазам.

```bash
node tools/design-sync.mjs extract "Playback Rental - прокат техники.html"
node tools/design-sync.mjs spec
node tools/design-sync.mjs audit apps/web/src   # базовый замер, до правок
```

Подробности — `docs/DESIGN-SYNC.md`. Коротко: бандл это не картинка, а полная
машиночитаемая спецификация всех пяти экранов; состояния в ней заданы нестандартными
атрибутами `style-hover`/`style-focus`, которые понимает только рантайм артефакта —
поэтому при первом (ручном) переносе они и потерялись. `spec` превращает их в обычный
CSS и в токены Tailwind v4.

Базовый замер на текущем коде: **86 из 89 переходов идут на дефолтной кривой Tailwind**
(`cubic-bezier(0.4,0,0.2,1)`), которой в дизайне нет ни разу — вместо дизайновской
`cubic-bezier(0.16,1,0.3,1)`. Плюс `duration-200` в 75 местах там, где в дизайне 240ms,
и три keyframes (`bnPop`, `bnRise`, `bnBar`) объявлены в `global.css`, но не вызываются
ниоткуда. Разметка и ховеры при этом перенесены почти полностью — потеряно именно
движение.

Чинить это сейчас, на Astro, смысла мало: Этап 2 всё равно переписывает разметку
витрины. А вот `tokens.css` и `interactions.css` — файлы, не привязанные к фреймворку,
и они переезжают как есть. Поэтому здесь только генерация и замер, применение — в
Этапах 1–3.

Одна поправка к записям: `CLAUDE.md` утверждает, что экран «Админка» брался из
`docs/design-reference/markup.html`. В markup.html его нет (там отрендерен только
экран `home`) — админка есть только в `template.html` и `dc_script.js`. Для Этапа 3
это важно: сверяться надо с ними.

**0.4 Смоук-чеклист.** Автотестов в проекте нет ни одного, вся верификация ручная —
это главный риск всего плана. Перед началом зафиксировать список сценариев, которые
прогоняются после каждого этапа:

- гость: главная → каталог → фильтр по категории → товар → выбор дат → в корзину → чекаут → заказ создан **с позициями** (тот самый баг из `mutate()`)
- админ: логин → каждая вкладка открывается с реальными данными
- админ: смена статуса заказа + заметка переживают перезагрузку
- админ: заведомо плохой `endDate < startDate` показывает сообщение хука, данные не меняются
- админ: загрузка картинки в категорию/акцию/товар
- админ: сохранение `SiteSettings` не теряет ни одного поля (`howItWorksSteps` остаётся 4 строки)

- `node tools/design-sync.mjs audit <перенесённое>` не добавил новых ⚠ к базовому замеру

- **Удалить прокси из `apps/web/src/middleware.ts`** (гвард `/admin/*` там пока оставить).
  Payload теперь same-origin для браузера, относительные `fetch('/api/...')` из Astro
  продолжают работать без изменений.

Проверка: сайт открывается на том же порту, ведёт себя идентично, только через Next.

## Этап 2 — Витрина

Порядок от безопасного к сложному:

1. Юр. страницы (`privacy-policy`, `user-agreement`) — чистая вёрстка, разогрев на маппинге
2. `how-it-works`, `contact` (+ остров `ContactForm`)
3. `index` — тянет `SiteSettings`, самый большой шаблон (297 строк)
4. `catalog/index`, `catalog/[slug]` + `CategorySidebar`, `ProductCard`, `CatalogPage`
5. `product/[id]` + острова `ProductPurchasePanel`, `RentalDatePicker`, `QuantitySelector`
6. `promotions/[slug]`
7. `checkout` — оставить напоследок, единственное место с мутацией

**Маппинг:**

| Astro | Next |
|---|---|
| frontmatter | тело `async function Page()` |
| `Astro.params` | `params` (в 15+ — `await params`) |
| `Astro.url.searchParams` | `searchParams` |
| `<slot />` | `children` |
| `client:load` / `client:visible` | `'use client'` в файле компонента |
| `<script>` в `.astro` | `useEffect` в клиентском компоненте |
| `Astro.locals` | аргументы / `cookies()` |

**Верстать по спеке, а не по глазам.** Это главный урок первого переноса. Для каждой
страницы источник истины — соответствующий блок `docs/design-reference/template.html`,
а не текущий `.astro`-файл. Порядок внутри страницы:

1. найти блок в `template.html` (по тексту или по `{{ }}`-биндингу);
2. перенести разметку, подставив на место inline-стилей утилиты Tailwind;
3. **каждому** `transition` явно проставить `ease-*` и `duration-*` из `tokens.css` —
   молчаливый дефолт Tailwind это ровно тот баг, который сейчас в коде 86 раз;
4. состояния взять из `interactions.css` — там уже лежат все 24 различных правила с
   исходными `transition` и комментарием, где в дизайне встречается каждое;
5. `animation:bn*` перенести вместе с задержкой — в дизайне их 34 на 9 keyframes,
   в коде сейчас 20.

Где в дизайне ховер родителя меняет ребёнка (обложка героя и фото товара —
`transform:scale(1.04)` на внутреннем слое), нужен `group` / `group-hover:`. Сейчас
в коде нет ни одного — эти два зума просто отсутствуют.

После каждой страницы — `node tools/design-sync.mjs audit` на перенесённое. К концу
Этапа 2 предупреждений по витрине быть не должно.

**Данные.** Завести `src/lib/data/*.ts` (server-only), где каждая функция из `lib/payload.ts`
переписывается на Local API:

```ts
const payload = await getPayload({ config })
const { docs } = await payload.find({ collection: 'categories', sort: 'order', limit: 100, depth: 1 })
```

Типы — прямо из сгенерированного `payload-types.ts`, `@playback-rental/shared-types` для
Next-кода больше не нужен (остаётся, пока жив Astro).

**Ловушка, которой в Astro не было: кэш Next.** У Astro `output: 'server'` — каждый запрос
живой. Next по умолчанию попробует закэшировать. Для каталога и товара это означает
устаревший сток и доступность. На всех страницах, читающих наличие, ставить
`export const dynamic = 'force-dynamic'` (или `noStore()` точечно) — и явно проверить это
в смоуке: изменить `quantity` в админке и убедиться, что каталог видит изменение сразу.

**Острова.** 8 `.tsx`-файлов (~1265 строк) переезжают почти дословно — React 19 с обеих
сторон. `nanostores` + `@nanostores/react` в Next работают как есть, `cart.ts` / `dates.ts`
не трогаем. Хак с `mounted` в `RentalDatePicker` **остаётся нужен** — у сервера по-прежнему
нет `sessionStorage`, природа hydration mismatch не изменилась.

**Чекаут.** `submitOrder()` из `lib/payload.ts` → Server Action на Local API. Хук
`beforeValidate` на `orderItems` остаётся единственным источником правды по ценам и
доступности — Local API вызывает хуки коллекций так же, как REST, никакой логики
дублировать не нужно. Обёртка `mutate()` умирает вместе с REST: `payload.create()`
возвращает документ напрямую, `{ doc, message }` — это артефакт исключительно REST-слоя.

`mediaUrl()` оставить как есть: возвращает относительный `/api/media/file/...`, который
теперь по-настоящему same-origin.

## Этап 3 — Админка (главный выигрыш)

**3.1 Аутентификация — сначала, всё остальное зависит.**

`apps/web/src/lib/admin/session.ts` удаляется целиком. Внутри Next:

```ts
const { user } = await payload.auth({ headers: await headers() })
```

Ни ручного чтения `payload-token`, ни `Authorization: JWT`, ни обхода CSRF-проверки —
вся эта конструкция существовала только потому, что запрос шёл между процессами.

**Гвард:** реальную проверку делать в `(admin)/layout.tsx` через `payload.auth`, а в
`middleware.ts` — максимум наличие cookie как дешёвый ранний редирект. Payload требует
Node-рантайма, и завязывать на него middleware не стоит. `/admin/login` и
`/admin/first-register` остаются вне гварда, каждая со своим редиректом, как сейчас.

**3.2 Шелл.** `AdminLayout.astro` → `(admin)/layout.tsx`. Навигация — `<Link>`, то есть
клиентские переходы без перезагрузки. Ради этого всё и затевалось.

**3.3 Чтение.** Все 7 эндпоинтов `apps/cms/src/endpoints/admin/*.ts` (`kpi`, `calendar`,
`clients`, `analytics`, `orders`, `orderDetail`, `stock`) перестают быть HTTP-эндпоинтами:
тело каждого становится server-only функцией, которую RSC вызывает напрямую. Убирается и
явная проверка `req.user` в каждом — она была нужна, потому что кастомные эндпоинты Payload
обходят access control коллекций; теперь гвард в layout один на всех.
`apps/web/src/lib/admin/api.ts` (152 строки типов и обёрток) удаляется.

**3.4 Мутации.** Браузерные `fetch()` → Server Actions + `revalidatePath()`.
`APIError` из хуков ловится в action и возвращается в форму через `useActionState` — тот же
баннер ошибки, что и сейчас, но без ручной обвязки. Проверить на том же сценарии
`endDate < startDate`.

Заодно уходит болезненный класс багов: дрейф порта 4321/4322, который молча ломал все
мутации 403-ми, при одном origin невозможен в принципе.

**3.5 Порядок страниц:**

1. `login`, `first-register` — без них не проверить остальное
2. шелл + `index` (KPI)
3. `orders` (список) → `orders/[id]` — самая сложная, статус/заметки/позиции/удаление/submit
4. `calendar`, `stock`, `clients`, `analytics` — read-only, быстро
5. `categories`, `promotions` (список + `[id]` с веткой `id === 'new'`), `products/[id]`
6. `media`, `users`, `settings`

`admin-media-upload.ts` (19 строк, общий для трёх форм) становится обычным клиентским
модулем — костыль с `define:vars` и рантайм-импортом `/src/scripts/...` был чисто
Astro-специфичным.

**3.6 Дизайн админки.** Правило Этапа 2 действует и здесь, с одной оговоркой: сверяться
надо с `template.html` / `dc_script.js`, а не с `markup.html` (см. 0.3 — экрана
«Админка» в markup.html нет вовсе). Из спеки сюда попадают, в частности, кривая с
перелётом `ease-overshoot` на столбцах календаря (`transform:scaleY(1.16)`) и на
крестике закрытия (`rotate(90deg)`) — сейчас в коде обе анимируются линейно.

Пять экранов админки дизайн не описывает вовсе (`Категории`, `Акции`, `Медиатека`,
`Пользователи`, `Настройки` — их дорисовывали по ходу Шагов 6–7 старого плана). Для них
спеки нет и не будет; ориентир — соседние, уже сверенные экраны.

## Оценка

| Этап | Дней |
|---|---|
| 0 — подготовка, апгрейд Next, спека дизайна, чеклист | 1–1.5 |
| 1 — каркас + разворот прокси | 0.5 |
| 2 — витрина (включая сверку с дизайном) | 2–2.5 |
| 3 — админка (включая сверку с дизайном) | 3–3.5 |
| 4 — уборка | 0.5 |
| **Итого** | **~7 рабочих дней** |

Сверка с дизайном добавила примерно день суммарно и вся сидит внутри Этапов 2–3:
разметка всё равно переписывается, разница только в том, откуда её брать. Отдельной
строкой она не выделена намеренно — это не задача «потом починить анимации», а способ
делать сам перенос.

## Риски

1. **Нет автотестов.** Самый серьёзный. Смягчается только дисциплиной чеклиста 0.3 после
   каждого этапа, а не в конце.
2. **Кэш Next вместо всегда-живого SSR Astro.** Молчаливый класс багов: устаревший сток
   в каталоге. Явно проверять, не полагаться на умолчания.
3. **Дизайн-система.** `global.css` тащить целиком одним куском. Раньше это был чисто
   визуальный риск («в целом похоже» вместо попиксельной сверки) — теперь у него есть
   машинная часть: `design-sync audit` ловит потерянные кривые, длительности и анимации.
   Всё, что audit не видит (пропорции, отступы, порядок блоков), по-прежнему проверяется
   глазами постранично.
4. **Известные болячки связки Next 15 + Payload + React 19.2** уже задокументированы в
   `next.config.mjs`. Этап 0.2 решает их до, а не во время миграции.
5. **Живые креды.** Отправка в МойСклад и вебхуки уведомлений не тестируются вживую,
   как и раньше.

## Что этот план не делает

Не трогает интеграцию с МойСклад, схему коллекций Payload, миграции БД, хуки
`orderItems`/`orders` и бизнес-логику цен. Это перенос слоя представления и доступа к
данным, ничего больше.

Дизайн он тоже не меняет — наоборот, приводит код к уже утверждённому. Если по ходу
захочется что-то в дизайне поправить, правка идёт в Claude Design, оттуда новый бандл,
`design-sync extract` + `spec` — и дальше по обычному кругу. Ручные правки в
`tokens.css` / `interactions.css` затрутся при следующем прогоне.
