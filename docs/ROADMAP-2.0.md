**Real bug found and fixed verifying `submitOrderToMoySklad` live**: it failed every time with "Unauthorized," under the same valid, unexpired admin session every other mutation on the same page succeeded under. Root cause: `payload.config.ts`'s `cors`/`csrf` allowlist is hardcoded to `WEB_URL`, and `apps/cms/.env.example` (the local, non-Docker dev copy — root `.env.example`/`compose.yaml` were already correct) still set it to `apps/web`'s own old address (`http://localhost:4322`), stale since Stage 1 made `apps/cms` the single public entry point. Payload's cookie-JWT strategy (`extractJWT`) checks the request's `Origin` header against that allowlist when present, falling back to `Sec-Fetch-Site` (satisfied by same-origin requests regardless of the allowlist) only when Origin is absent. A plain page navigation typically carries no Origin at all, so every Server Component auth check kept succeeding — but a Server Action's own internal POST does send Origin, so every session-reading Server Action was silently rejected. This is also why Stage 1/2 never surfaced it: their only prior Server Action (checkout's `submitCheckout`) is anonymous and never calls `payload.auth()`. **Fixed** by correcting `WEB_URL` to `http://localhost:3000` (this app's own local address) in `apps/cms/.env.example`, with that file's comment and `payload.config.ts`'s neighboring `cors`/`csrf` comment both rewritten to state `WEB_URL` has meant this app's own public origin since Stage 1, not `apps/web`'s. Root-caused via a bare 10x `payload.findByID()` loop outside Next (10/10 succeeded, ruling out a DB/Payload-level bug), a temporary header dump inside `getAdminUser()` (cookie present and byte-identical on every call, ruling out a missing-cookie theory), and reproducing the identical failure under a genuine `next build && next start` production server as well as `next dev` (ruling out a dev-mode/Turbopack artifact) before reading Payload's own `extractJWT` source.     - `(frontend)/page.tsx`'s `allProductsResult` fed **five** different consumers — `fromPrice`, `freeNowCount`, `categoryStats`, `marqueeNames` and `totalDocs` — which is exactly why `limit: 1` would have silently broken four of them. It is asked only about the subtrees of the tiles actually rendered, and it cannot join the page's `Promise.all` — which categories to aggregate is only known once `getCategories()` has resolved.
    - Verified by parity, not by inspection: a script recomputed the pre-change algorithm from raw REST data over a deliberately awkward seeded catalog (a 0 ₽ rental, a zero-quantity product, an `available: false` product, sale vs. rental, a category with no products, a two-level category tree) and asserted the live rendered pages show exactly those values — all five homepage consumers plus the accessories strip for every one of the nine products.
