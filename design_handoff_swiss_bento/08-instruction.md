## 1. Как доставляется дизайн

Не копированием кода из прототипа, а конвейером репозитория:

```bash
node tools/design-sync.mjs extract "Playback Rental - прокат техники.html"
node tools/design-sync.mjs spec
node tools/design-sync.mjs audit apps/cms/src
```

- `extract` разбирает бандл дизайна (машиночитаемая спецификация экранов, не картинка);
- `spec` пишет `docs/design-reference/spec/tokens.css` (кривые, длительности как утилиты
  Tailwind v4) и `interactions.css` (24 правила состояний) — оба импортируются из
  `apps/cms/src/styles/global.css`;
- `audit` сверяет код с дизайном и печатает расхождения.

Бандл лежит в `reference/Playback Rental - прокат техники.html` этого пакета — положить
в корень репозитория, если его там ещё нет.

Правки дизайна идут **в бандл**, оттуда `extract` + `spec`. Не в сгенерированные CSS.

Токены цвета, радиусов, теней и шрифта уже объявлены в `@theme` внутри
`apps/cms/src/styles/global.css` и **соответствуют дизайну**. Новых токенов не заводить:
система закрыта. Шрифт — Golos Text, self-hosted в `apps/cms/public/fonts`, не Google Fonts.

## 2. Порядок работ

Пять блоков. Внутри блока можно параллелить, блоки — последовательно.
Каждый пункт — отдельный PR с базой `2.0`.

### Блок A — Деньги и сток (первым, меняет состав экранов)

**A1. Одна конвенция суток.** `07-audit-apps-cms.md` N1, N2.

Сейчас два файла считают одно и то же и одинаково ошибаются:
`apps/cms/src/lib/pricing.ts` («display-only», комментарий ссылается на удалённый
`apps/web`) и `apps/cms/src/lib/rental/pricing.ts` (серверная правда, вызывается хуком
`beforeValidate` на `orderItems`).

```ts
const hours = Math.ceil((endDate.getTime() - startDate.getTime()) / (1000 * 60 * 60))
return Math.ceil(hours / 24) || 1
```

Проблема: 12 авг 10:00 → 14 авг 10:00 = 2 смены, но календарь подсвечивает 3 дня и
техника у клиента трое суток. Плюс результат зависит от часа возврата: то же 12→14 авг
в 18:00 даёт 3 смены.

Сделать:
- единственный источник — `lib/rental/pricing.ts`; `lib/pricing.ts` свести к реэкспорту
  или удалить; вычистить комментарии про `apps/web`;
- конвенция — календарные сутки владения, включая день выдачи и день возврата:
  `Math.max(1, differenceInCalendarDays(end, start) + 1)`;
- записать конвенцию в JSDoc функции;
- время выдачи/возврата остаётся информацией для менеджера, на цену не влияет;
- привести к той же конвенции `lib/dateRange.ts`;
- правило «минимум одни сутки» живёт в функции цены, а не в одном из мест выбора дат.

*Приёмка:* равные даты дают одни полные сутки и полную ставку; витрина и хук
`beforeValidate` дают одно число; юнит-тест `price(base, d) === base * d` для d = 1…30;
цена не зависит от выбранного времени.

**A2. Rate-limit и срок жизни брони.** G1 — самая дорогая проблема.

Ни на одном пути записи нет ограничения частоты (`submitOrder`, форма контактов,
`/api/users/login`). Занятость считается по статусам `pending` + `confirmed`
(`ACTIVE_STATUSES`), а у `pending` нет ни срока жизни, ни автоотмены. Один публичный
скрипт оформляет заявки на весь остаток позиции и держит «Забронировано» бессрочно.

Сделать:
1. rate-limit на Server Actions по IP + телефону (заявок в час), на логин — по IP;
2. поле `holdUntil` на заказе: по умолчанию +24 ч или до начала аренды, что раньше;
3. крон переводит просроченные `pending` в новый статус `expired`; `expired` сток не занимает;
4. занятость считать по `confirmed` + `pending` с непросроченным `holdUntil`;
5. в админке — фильтр «истекающие брони».

*Приёмка:* серия заявок с одного IP отбивается; просроченная бронь освобождает сток без
участия оператора; в корзине есть состояние «бронь держим до 18:00».

Пункт 3 добавляет статус — обновить `ORDER_STATUS_TONE` и `STATUS_OPTIONS` в
`OrderDetailForm`, легенду календаря и `ACTIVE_STATUSES`.

**A3. Русские ошибки вместо `APIError`.** G5.

Хук `OrderItems` бросает `endDate must be after startDate`,
`Only a limited quantity of ... is available`. `submitOrder` их не переводит,
`error.message` печатается в корзине как есть.

Сделать: хук бросает коды (`RENTAL_DATES_INVALID`, `RENTAL_QUANTITY_UNAVAILABLE`,
`RENTAL_MIN_DURATION`), клиент показывает русский текст **с действием**: сколько
доступно, какие даты свободны, кнопка «изменить даты». Английские строки — только в логи.

*Приёмка:* ни одна ошибка чекаута не показывает клиенту английский текст.

**A4. Занятая позиция не уезжает в заявку молча.** N10.

`CheckoutPage.tsx` пишет у занятой позиции «проверим при звонке» и не мешает отправке;
`validate()` про доступность не знает; `getRentalAvailabilityBulk` падает в пустой
`.catch(() => {})`, из-за чего ошибка сети неотличима от «всё свободно».

Сделать: явное предупреждение с выбором — «убрать» / «изменить даты» / «оставить,
менеджер подтвердит». Ошибку загрузки показывать ошибкой.

### Блок B — Флоу дат и корзина

**B1. Развилка «сначала даты».** G4 — главная точка отвала.

Кнопка «В корзину» без дат превращается в «Выберите даты аренды» и не делает ничего:
не открывает модалку, не подсвечивает поле. В каталоге кнопка добавления есть на каждой
карточке, а даты выбираются на карточке товара — из каталога добавить нельзя вообще.

Минимум: нажатие на неактивную кнопку **открывает** модалку дат — это следующий шаг, а
не ошибка ввода. Плюс один выбор дат на сессию сверху каталога.

Лучше: разрешить добавление без дат и спрашивать даты в корзине одним блоком на все
позиции — короче на шаг и снимает B2. Решение за продуктом; текущее состояние хуже обоих.

**B2. Корзина без дат показывает нули.** N4.

Корзина в `localStorage` (`persistentJSON('pb:cart')`), даты — в `sessionStorage`
(`stores/dates.ts`). Новая вкладка или следующий день: позиции на месте, дат нет →
`calculateRentalPrice(price, undefined, undefined)` = 0 → всё «0 ₽».

Сделать: без дат не показывать нули — в строке позиции ставка («4 000 ₽ / сутки»), в
итоге «Выберите даты, чтобы рассчитать». Либо хранить даты рядом с корзиной и показывать
с пометкой «даты из прошлой сессии, проверьте».

**B3. Состав расчёта в корзине.** N3 — это блок макета, а не строка.

Сейчас `CheckoutPage.tsx` печатает «Аренда за смену» = `total` = `$cartTotal`, который уже
включает смены и количество. На 3 смены по 4 000 ₽ клиент видит «Аренда за смену
12 000 ₽» и «К оплате 12 000 ₽» — одно число под двумя подписями, одна из них ложь.

Сделать как в дизайне и как уже сделано на карточке товара:
Ставка за смену → Срок → Позиций → **К оплате**. Ставка = сумма `price × quantity` по
позициям, итог = ставка × смены. Скидок за срок нет. Скидка **набора** (разница между
суммой позиций и ценой набора) остаётся.

**B4. Часы работы — одно значение.** N5.
`lib/dateRange.ts`: `BUSINESS_HOURS = { open: 9, close: 21 }` → в сетке есть 09:00.
Подпись под той же сеткой: «Рабочие часы 10:00 — 21:00». Взять из `SiteSettings`, убрать
константу и строку в JSX.

**B5. Плюрализация.** N6. `CheckoutPage.tsx` в двух местах даёт «5 смены».
`formatShifts()` и `pluralizeRu()` уже есть в `lib/dateRange.ts`.

**B6. Согласия — нативные чекбоксы.** N12. `CheckBox` в `CheckoutPage.tsx` — это
`<div onClick>`: ни `role`, ни `tabIndex`, ни `input`, с клавиатуры не поставить. При этом
они блокируют отправку, и один из них — согласие на обработку ПДн.
Сделать `<input type="checkbox">` в `<label>`, визуал сохранить.

### Блок C — Скорость (разметку не меняет)

**C1. `next/link` на всей витрине.** G2. Сейчас переходы — обычные `<a href>`: полная
перезагрузка, белая вспышка, потеря скролла. В админке `next/link` уже используется.

**C2. Разобрать `force-dynamic`.** Стоит подряд, включая страницы, где сток не читается
(правовые, «как это работает», главная). Оставить только там, где читается сток и
занятость: каталог, карточка товара, корзина. Остальное — статика или `revalidate`.
Осторожно: устаревший сток в каталоге — известный класс багов этого переезда.

**C3. Не проигрывать вход-анимацию при возврате.** `bnIn 560ms` со стаггером до 400 мс
на каждый блок: после перезагрузки контент ещё полсекунды приезжает. При навигации
назад/вперёд не запускать.

**C4. Картинки.** G3. `next/image` не используется ни разу; `mediaUrl()` отдаёт
оригиналы; единственный объявленный `imageSize` (`thumbnail 400×400`) не используется
нигде. Сетка каталога = 12–24 полноразмерных файла, без `srcset`, без `width`/`height`
(отсюда сдвиг layout), без ленивой загрузки.

Сделать: размеры под реальные слоты (карточка каталога, превью галереи, обложка героя,
миниатюра в корзине и в админке); `next/image` с `sizes`; `priority` только на обложке
героя; остальное `lazy`; проверить, что `next.config` пропускает домен МойСклада.

**C5. Каталог: два лишних запроса.** N7, N9. `getProducts({ limit: 100 })` без пагинации
— каталог молча обрезается, а счётчик `products.length` покажет «100 позиций» и соврёт.
Отдельно `getProducts({ limit: 500 })` тянется только ради счётчиков сайдбара — заменить
агрегирующим `count` по категориям.

**C6. Поиск теряет раздел.** N8. Форма отдаёт `q` и `sort`, но не `kit`: поиск из
«Наборов» выбрасывает в общий каталог.

### Блок D — Админка оператора

**D1. Правка позиции пишет на каждое нажатие клавиши.** N17 🔴
`OrderDetailForm.tsx`: количество и даты на `onChange`, а не `onBlur`. Ввод «12» = два
Server Action вызова (сначала `quantity: 1`), каждый с пересчётом цены и хуком. Стирание
поля даёт `Number('')` = 0 и запись нуля. Подпись под таблицей при этом обещает
обратное: «сохраняются автоматически при потере фокуса».
Сделать: `onBlur`, `Number.isFinite` + минимум 1, откат значения в поле при неуспехе.

**D2. Статус меняется в интерфейсе, даже если сервер отказал.** N18
`handleStatusChange` делает `setStatus(value)` до запроса и не откатывает. Оператор видит
«Подтверждён», в базе `pending`. То же с `defaultValue`-инпутами позиций.

**D3. «Сумма» заказа не пересчитывается.** N19 Карточка печатает `order.totalPrice` из
пропса; `handleItemFieldChange` обновляет `lineTotal` позиции, но не итог.
`router.refresh()` вызывается только после отправки в МойСклад.

**D4. Календарь занятости.** N20 — две реализации:
`app/(admin)/admin/calendar/page.tsx` и `components/admin/CalendarView.tsx` (кастомная
вьюха штатной админки на `DefaultTemplate`). Свести к одной. По существу:
- дефицит не виден — полоса не сравнивается с `product.quantity`: товар в 5 шт. с бронью
  на 1 шт. и забронированный целиком выглядят одинаково;
- полосы перекрываются — все позиции товара в одном `<td colSpan>` с
  `position:absolute; top:6`; два пересекающихся заказа накладываются, верхний прячет
  нижний (ровно то, что оператору важнее всего);
- только 14 дней вперёд, без навигации — заявку на следующий месяц не проверить;
- полоса не ведёт в заказ, номер только в `title`;
- `products.find({ limit: 0 })` тянет весь каталог, фильтрация в JS.

**D5. Поиск и фильтры.** N21 (старый пункт 15, не закрыт). Очередь заявок — без фильтра
по статусу и поиска по телефону; склад — вся таблица без поиска и фильтра по категории.

**D6. Пять экранов без дизайна.** N22 — Категории, Акции, Медиатека, Пользователи,
Настройки. В макете их нет (`AdminSidebar` фиксирует это в комментарии). Перед вёрсткой
запросить решение: оставить по образцу соседних экранов или описать в `04-screens.md`.

## 4. Где прототип не источник истины

Прототип — правда про внешний вид и поведение. Про данные правда — репозиторий:
город, часы работы, цены, состав полей формы, названия статусов. Где расходятся —
верить репозиторию и сообщить о расхождении.

Иконок в дизайне почти нет: стрелки и знаки набраны текстом (`→ ← + − ✓ ✕ ↺ ◆`).
Оставить текстом — это часть свисс-характера, не заменять иконочным шрифтом.
Логотип в шапке текстовый (`PLAYBACK` 700 / `RENTAL` 400 / `®` акцентом); svg — только
favicon и OG.

## 5. Порядок сдачи

По каждому PR в описании: что закрыто (номер из `07-audit-apps-cms.md`), как проверить,
что осталось. Перед каждым PR по витрине — прогон:

```bash
node tools/design-sync.mjs audit apps/cms/src
```

Пять пунктов, которые важно закрыть раньше остального, потому что от них зависит
состав экранов: **A1** (сутки), **A2** (сток и брони), **B3** (расчёт в корзине),
**B1** (флоу дат), **A3** (русские ошибки).
