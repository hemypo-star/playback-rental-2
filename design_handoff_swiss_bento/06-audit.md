# A. Логика аренды и дат (п. 1–7)

## 1. 🔴 Две разные конвенции подсчёта суток

`src/utils/pricingUtils.ts`:
```ts
const days = Math.ceil((endDate.getTime() - startDate.getTime()) / millisPerDay);
```
`src/utils/dateUtils.ts`:
```ts
export const calculateDaysDifference = (start, end) => differenceInDays(end, start) + 1;
```

Первая считает 12→14 авг как **2 суток**, вторая — как **3**. Цена берётся из первой,
а «×3 суток» в интерфейсе может прийти из второй. Пользователь видит расчёт, который не сходится.

**Сделать:** одна функция `getRentalDays(start, end)` в `pricingUtils`, единственный источник
истины, вызывается и в товаре, и в корзине, и в админке. Явно решить и записать в JSDoc:
аренда 12→14 авг — это 3 суток (включая день выдачи и день возврата) или 2. Прокат техники
обычно считает по календарным суткам владения → **3**. Тогда цена в дизайне
(«12–14 авг · 3 суток») сходится.

## 2. 🔴 Скидки за срок удалить — цена линейная по суткам

**Принятое решение (сентябрь 2026): скидок за длительность нет.**
Цена = ставка за сутки × число суток. Ничего больше.

**Статус на `2.0`: закрыто.** Ниже — как было в `main`, для истории.

Было в `pricingUtils.calculateRentalPrice` скидка 10% от 3 суток и **30% от 5 суток**,
и эта шкала к тому же немонотонна — при базе 1000 ₽ четверо суток стоят 900 × 4 = 3600 ₽,
а пятеро 700 × 5 = 3500 ₽. Пять суток дешевле четырёх.

**Сделать:** выпилить скидки целиком.

```ts
/** Суток аренды: включая день выдачи и день возврата. Минимум — 1 сутки. */
export const getRentalDays = (start?: Date, end?: Date): number => {
  if (!start || !end || isNaN(+start) || isNaN(+end)) return 0;
  const a = startOfDay(start), b = startOfDay(end);
  return Math.max(1, differenceInDays(b, a) + 1);
};

/** Цена аренды. Линейная: ставка × сутки. Скидок за срок нет. */
export const calculateRentalPrice = (basePrice: number, start?: Date, end?: Date): number => {
  const days = getRentalDays(start, end);
  return days === 0 ? 0 : Math.round(basePrice * days);
};
```

Удалить: `calculateRentalDetails` (её поля `discount`, `dayDiscount`, `hourlyRate`
больше не нужны), `calculateHourlyRate`, все ветки `hours <= 4`, все пороги
`days >= 3` / `days >= 5`. Проверить, кто их импортирует
(`PricingCalculator.tsx`, `useCart.tsx`, страница товара, админка) — и убрать
из интерфейса строки про скидку.

Юнит-тесты: `price(base, d) === base * d` для d = 1…30; `days(same, same) === 1`;
`price(base, вчера, вчера) === base`.

**Важно:** скидка в **наборах** («выгода 450 ₽») к этому не относится — это разница
между суммой позиций набора и ценой набора, а не скидка за срок. Она остаётся.

## 3. 🔴 Меньше суток = одни сутки. Почасовую логику удалить

**Принятое решение: минимальный срок аренды — 1 сутки.** Любой выбор короче суток
(один и тот же день, несколько часов) считается как полные сутки по полной ставке.

Сейчас: `start` и `end` — один день (обе даты в 00:00, как их отдаёт календарь) →
`end - start = 0` → `days = Math.ceil(0) = 0` → `hours = 0` → срабатывает ветка
`hours <= 4` и возвращается `basePrice * 0.7`. Суточная аренда считается 4-часовой
и стоит 700 ₽ вместо 1000 ₽, а при `days = 0` в других местах итог обнуляется.

**Сделать:** `Math.max(1, …)` в `getRentalDays` (код в п. 2) и удалить всю почасовую
логику: ветки `hours <= 4`, `calculateHourlyRate`, `hourlyRate` из возвращаемых
объектов. Слоты времени (`getAvailableTimeSlots`, `getBusinessHoursOptions`) остаются
**только** как время выдачи и возврата внутри рабочего дня — на цену они не влияют.

В интерфейсе: строка «1 сутки» показывается всегда, даже если выбран один день.
Подпись под расчётом — «Минимальный срок аренды — 1 сутки» (12.5px, muted).

## 4. 🟡 Часы работы расходятся в трёх местах

`dateUtils.getBusinessHoursOptions` и `getAvailableTimeSlots` по умолчанию **8:00–22:00**.
Дизайн в шапке заявляет **Пн–Вс 10:00–20:00**. Контакты — третье значение.

**Сделать:** одно значение в `settingsService`, читается и шапкой, и генератором слотов,
и контактами. В дизайн подставить то, что реально. То же — про город и адрес:
источник истины — репозиторий, не прототип.

## 5. 🟠 Проверка занятости запрещает выдачу в день возврата

`dateUtils.isDateRangeAvailable`:
```ts
if (startMs <= bookedEndMs && bookedStartMs <= endMs) return false;
```
Границы включительные. Бронь «10–12 авг» блокирует новую бронь «12–14 авг», хотя
12-го камера уже вернулась. При обороте в 1–2 дня это заметная часть потерянной выручки.

**Сделать:** решить, что означает `end` — момент возврата или последние занятые сутки —
и сделать интервалы полуоткрытыми `[start, end)`. Оставить один буферный день только
если он нужен бизнесу (осмотр/чистка), и тогда **показать его в календаре** как
«техобслуживание», а не прятать в неравенстве.

## 6. 🟠 Расчёт должен быть виден целиком

Скидок больше нет (п. 2), поэтому расчёт стал простым — и тем важнее показать его
полностью, чтобы итог не выглядел взявшимся из воздуха.

**Сделать:** на товаре и в корзине одна и та же раскладка, строка в строку:

```
Ставка              1 200 ₽ / сутки
Срок                3 суток            (12–14 авг)
Количество          × 2
─────────────────────────────────────
К оплате            7 200 ₽
```

Все числа — из одной функции `calculateRentalPrice`, ни одного расчёта в вёрстке.
Строк «Скидка», «Выгода», «Экономия» на страницах товара и корзины быть не должно —
проверить `PricingCalculator.tsx` и убрать. Единственная «выгода» в продукте —
в готовых наборах, и она про состав, а не про срок.

## 7. 🟡 Отладочный вывод и часовые пояса

`isDateRangeAvailable` содержит два `console.log` с телом брони — уйдёт в прод.
Даты в брони приходят из Supabase строками и превращаются в `Date` без нормализации;
`startOfDay` применяется только к «сегодня».

**Сделать:** убрать `console.log`; все даты бронирований пропускать через `startOfDay`
при гидрации; хранить в БД как `date`, а не `timestamptz`, если время не используется.

кнопка «назад» ведёт себя непредсказуемо.

Плюс в каталоге **нет сортировки** вообще, хотя строка сортировки заложена в дизайне,
и нет фильтра по цене.

**Сделать:** все фильтры в `useSearchParams` (`?category=&q=&from=&to=&sort=&priceMin=&priceMax=`),
`location.state` не использовать. Сортировка: по цене ↑↓, по названию, по новизне.

# C. Корзина и оформление (п. 11–14)

## 11. 🔴 Валидация формы работает через перехват кликов по тексту кнопки

`src/components/checkout/CheckoutForm.tsx`:
```ts
document.addEventListener('click', (e) => {
  if (target.closest('button')?.textContent?.includes('Оформить заказ')) { … }

```

Валидация привязана к **строке в надписи кнопки**. Переименование кнопки (а редизайн
её переименует — в дизайне это «Отправить заявку») молча выключает всю валидацию:

**Сделать:** обернуть в `<form onSubmit>`, кнопка `type="submit"`, валидация в
обработчике submit. Состояние ошибок и «была ли попытка отправки» — в состоянии формы.
Идеально — `react-hook-form` + `zod` (в проекте уже есть оба, судя по shadcn-набору).
Слушатель на `document` удалить.

## 14. 🟠 Корзина: устаревшие даты, спам уведомлений, сеть на каждый клик

`src/hooks/useCart.tsx`:

1. Корзина восстанавливается из `localStorage` **без проверки актуальности дат**.
   Через неделю пользователь открывает сайт и видит корзину с прошедшими датами;
   `calculateRentalPrice` для них вернёт мусор, а `isDateRangeAvailable` уже вернёт `false`.
   → При гидрации: даты в прошлом — сбросить, показать в корзине плашку
   «Даты устарели, выберите новые», позиции сохранить.
2. **Каждое** изменение количества — два сетевых запроса (`getProductById` +

   10 запросов и 5 всплывашек. Степпер P14 с `bn-pop` даёт обратную связь мгновенно
   и без сети.
   → Проверять доступность **дебаунсом** (300–400мс) и один раз при отправке заявки;
   максимум держать в состоянии позиции. Toast — только на ошибку («доступно 2 шт.»),
   не на успех.
3. Toast на добавление, удаление, изменение количества, смену дат — четыре подряд.
   → Убрать все успешные toast. Добавление в корзину подтверждается пульсом счётчика

4. `updateCartDates` ставит **одни даты всем позициям**, но `CartItem` хранит даты
   на каждой позиции. Два противоречащих друг другу режима.
   → Решить: либо одна дата на всю заявку (тогда убрать даты из `CartItem` и

5. Успех оформления — сейчас редирект/toast. → Заменить панель итога карточкой с номером

# F. Доступность (в рамках п. 20 и PR 9)

🟠 Находки:

1. `--ring` в старой теме — синий (`222 47% 11%` для foreground, `--ring` от той же
   палитры). В новом `index.css` фокус чёрный и видимый. Проверить, что нигде не
   осталось `focus:outline-none` без замены.
2. В дизайне много интерактивных `div` (ограничение прототипа). В проде **всё**
   должно быть `<button>` / `<a>`: карточки товара, дни календаря, строки таблиц,
   пункты фильтров, чипы. Дни календаря — `<button>` с `aria-pressed` и
   `aria-disabled` для занятых.
3. Статус нигде не должен передаваться только цветом. Чипы P7 и бейджи P13 уже
   содержат слово — не заменять на цветную точку.
4. Модалка дат: `role="dialog"`, `aria-modal`, фокус-ловушка, `Esc`, возврат фокуса
   на кнопку-открывашку. Radix `Dialog` это умеет — использовать его, не свой.
5. Контраст: `#75736E` на `#EFEEEB` = **4.6:1** — проходит AA для текста ≥12.5px;
   на белом 4.9:1. Красный `#D62410` на белом — 5.1:1. Всё в норме, но
   **не осветлять `pb-muted`** и не пускать его на цветные подложки.
6. Бегущая строка и пульс индикатора — бесконечные анимации; `prefers-reduced-motion`
   должен их останавливать (правило в `index.css` есть, но `animation-iteration-count: 1`
   для `bn-mark` оставит строку в конечном положении — проверить визуально).
7. `alt` у изображений товаров: сейчас, судя по `ProductImage`, подставляется название.
   Для декоративных фото (hero, категории) — `alt=""`, чтобы скринридер не зачитывал.
8. Язык документа: проверить `<html lang="ru">` в `index.html`.

# H. Производительность фронта (п. 22)

🟡 Находки:

1. **Двойной smooth-scroll.** `html { scroll-behavior: smooth }` в старом CSS +
   `window.scrollTo({ behavior: 'smooth' })` в `Catalog.tsx` → рваная анимация.
   Новый `index.css` глобальное правило убрал.
2. **`useMemo` вокруг всего дерева приложения** (`App.tsx`, `appContent` с пустым
   массивом зависимостей) — не даёт ничего: дети всё равно перерисовываются от
   контекстов. Убрать, чтобы не вводить в заблуждение.
3. **Каталог грузится не лениво**, а комментарий в коде объясняет это как решение
   («Direct import for Catalog instead of lazy loading»). Это увеличивает первый бандл.
   Лучше вернуть `lazy` + `prefetch` при наведении на ссылку «Каталог».
4. **`seedDatabase()` и `resetStoragePermissions()` при каждом монтировании `App`.**
   В проде это лишние запросы на старте (а seed — потенциальная запись данных).
   Оставить только для dev по флагу окружения.
5. **`ProductCard.tsx` (7.1 КБ) и `ProductCardMemo.tsx` (8.1 КБ)** — почти дубликаты.
   Редизайн придётся делать дважды, и они разъедутся. Слить в один с `React.memo`.
6. **`VirtualizedProductGrid`** при типичном каталоге в 50–200 позиций даёт больше
   проблем (ломает sticky, скачет высота, мешает Ctrl+F), чем выигрыша. Проверить
   реальное число товаров; если < 300 — заменить на обычную сетку с `content-visibility`
   на карточках (не на `img`, как было).
7. **Composite-хаки** из старого `index.css` (`.grid { transform: translateZ(0) }`,
   `img { content-visibility: auto; contain-intrinsic-size: 200px 200px }`,
   `.card { perspective: 1000px }`) — создавали слой на каждой сетке и карточке,
   ломали `sticky` и размывали текст. Удалены в новом файле; не возвращать.
8. **CLS.** Все медиа обязаны иметь `aspect-ratio` (P5) и подложку `#E6E4E0`.
   Скелетоны — того же размера, что карточки.
9. **Шрифт.** Golos Text четырьмя весами через `&display=swap` + `preconnect`.
   Если FOUT мешает — сузить до 500/600 (400 нужен только для слова «Rental» и абзацев,
   700 — для лого и счётчика; можно обойтись тремя весами: 400/500/600).
10. `App.css` рядом с `index.css` — остаток шаблона Vite. Проверить и удалить.
11. `refetchOnWindowFocus: false` глобально — для админки это неверно: оператор
    возвращается во вкладку и видит устаревшие заявки. Включить для админских запросов.
